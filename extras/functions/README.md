# Project Admin lifecycle email functions

`notifyWorkItemLifecycle` watches `workItems/{itemId}` for every configured work
kind and sends only action-required and final-outcome messages. Delivery attempts are recorded in the admin-only
`notificationAttempts` Firestore collection and use the CloudEvent id as the
stable SMTP message id.

This is an optional extra (`extras/README.md`) for the firestore backend only:
it triggers on Firestore documents. Install it with `npm run install:extras` and
test it with `npm run test:functions`; `firebase.json` points
`functions.source` here.

Before the first deployment:

1. Store the SMTP credentials without printing or writing them to the repo:

   ```sh
   eval "$(node scripts/project-env.js shell)"
   firebase functions:secrets:set EMAIL_USER --project "$PROJECT_ID"
   firebase functions:secrets:set EMAIL_PASS --project "$PROJECT_ID"
   ```
2. Deploy `notifyWorkItemLifecycle` (`firebase deploy --only functions:notifyWorkItemLifecycle`).
3. Verify a real lifecycle transition reaches the configured mailbox and that its matching
   `notificationAttempts` document is marked `sent` with provider `gmail_smtp`.

Messages authenticate as `EMAIL_USER`; their project name, fallback owner email,
admin URL, and per-kind labels/prefixes/routes come from
`extras/functions/project-config.json` (the `workKinds` entry is generated by
`npm run sync:work-kinds`). Active users with the
`admin` role are notification recipients.

## Delivery preferences and email throttling

Every work-item event still produces one notification, but each recipient's
`adminUsers/{email}.notifications` record decides which channel carries it:

| Event type | Email default | Push default |
|---|---|---|
| `action_required` (a human gate entry) | on | on |
| `deployment_failure` | off | on |
| `deployment_progress` | off | on |
| `final_outcome` (shipped/closed) | on | on |

Preferences are edited per user on the admin console Users page and stored as
`notifications.email.<type>` / `notifications.push.<type>` booleans; missing
keys use the defaults above. A deployment failure that also enters the
question gate counts as `action_required` for anyone who muted failure alerts,
so muting the noisier type never hides the gate itself.

Two server-side rules apply on top of the preferences:

- `deployment_failure` fires once per entry into the question gate. Later
  thread messages while the item still sits at that gate never re-alert.
- Email for the same gate (or the same final outcome) on the same item is sent
  at most once per 24 hours, tracked in `notificationGateState/<collection>-<id>`
  and keyed by gate. A bounce back into the gate inside that window is push-only.

Suppressed deliveries are recorded in `notificationAttempts` with
`state: 'suppressed'` and a `suppressedReason` of `recipient_preferences` or
`gate_email_window`, so "why did I not get an email" is answerable from the
attempt log.
